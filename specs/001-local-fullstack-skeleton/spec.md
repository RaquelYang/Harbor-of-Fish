## User Scenarios & Testing *(mandatory)*

### User Story 1 - 啟動並查看本機測試流程 (Priority: P1)

開發者依 repository 說明啟動本機資料庫、API 及前端，並在繁體中文測試頁查看由資料庫讀出的固定測試資料。畫面及 API 回應都清楚標示資料僅供測試，不代表任何真實漁港、魚種或行情內容。

**Why this priority**: 這是本階段的主要交付，讓新環境能重現並直接觀察 Angular 到 API 再到資料庫的端到端資料流程。

**Independent Test**: 從空白的本機開發資料庫依說明啟動整個流程，確認 Flyway 建立所需結構，測試頁顯示 API 讀取到且帶有測試標記的資料。

**Acceptance Scenarios**:

1. **Given** 本機資料庫為空且依賴已安裝，**When** 開發者依文件啟動資料庫與 API，**Then** 資料庫結構由版本化遷移建立，且 API 啟動成功。
2. **Given** API 與前端均已啟動，**When** 開發者開啟繁體中文測試頁，**Then** 頁面透過前端集中且具型別的 API 存取層取得測試資料，並同時呈現明確的測試用途標記。
3. **Given** 測試資料已持久化，**When** 開發者停止並重新啟動本機服務，**Then** 測試頁再次顯示相同測試資料及標記。

---

### User Story 2 - 重複載入並安全重設測試資料 (Priority: P2)

開發者可依記錄的格式與欄位規則載入固定測試資料，重複執行載入不會產生重複或互相矛盾的資料；需要重來時，可只清除本機開發資料並重新載入。

**Why this priority**: 可重複的測試資料使驗收及除錯結果穩定；明確限制重設範圍可避免把本機清除步驟誤用於正式資料。

**Independent Test**: 連續執行測試資料載入兩次，比較筆數及內容一致；取得使用者對清除命令及目標資料庫的另行明確授權後，再依文件清除本機開發資料並重新載入，確認可恢復相同初始狀態。未獲授權時，允許清除與重載結果維持待驗證。

**Acceptance Scenarios**:

1. **Given** 初始資料已載入，**When** 再次執行相同載入程序，**Then** 記錄數及欄位值維持一致，不新增重複記錄。
2. **Given** 測試資料檔格式正確，**When** 載入程序檢查每筆資料，**Then** 所需欄位及值符合已記錄的欄位驗證規則。
3. **Given** 開發者要重設環境，且使用者已就清除命令與目標資料庫另行明確授權，**When** 使用文件中明確限定本機開發資料的清除程序，**Then** 本機測試資料可被清除及重建，且該程序不會指向正式環境或正式資料；未獲授權時不得執行清除。
4. **Given** 固定資料準備完成，**When** 檢查版控資料及設定範例，**Then** 不包含真實個資、真實憑證或來源未授權內容，也不暗示固定測試值是真實產品資料。

---

### User Story 3 - 確認錯誤狀態與各端驗收命令 (Priority: P3)

開發者可確認 API 成功及錯誤回應、資料讀寫與遷移行為，並在前端看到易懂的載入、成功及失敗狀態。文件提供實際在本機執行成功的安裝、啟動、測試、lint、build 與冒煙流程命令。

**Why this priority**: 明確的錯誤呈現與可重跑驗收步驟能降低本機環境差異，並為後續功能開發提供可信的品質基線。

**Independent Test**: 分別在 API 可用及 API 不可用的情境載入測試頁，確認成功及錯誤狀態；執行文件列出的前後端驗證命令與跨端冒煙流程，確認命令及結果有記錄。

**Acceptance Scenarios**:

1. **Given** 測試資料存在且 API 可用，**When** 呼叫版本化測試端點，**Then** API 回傳符合契約的資料、明確測試標記及成功狀態。
2. **Given** 請求格式錯誤或必要服務不可用，**When** 呼叫端點或載入測試頁，**Then** API 使用一致且不洩漏內部資訊的錯誤回應，前端呈現可理解的失敗狀態。
3. **Given** 前後端與資料庫骨架完成，**When** 開發者依文件執行已驗證的命令，**Then** 前端與後端測試、正式建置、Flyway 啟動驗證及本機跨端冒煙流程均有可重現的結果記錄。

### Edge Cases

- 資料庫尚未啟動、連線設定錯誤或 API 無法連線時，前端顯示失敗狀態，不顯示先前快取或假裝成功的測試資料。
- Flyway 遷移失敗或資料庫 schema 與程式預期不符時，API 不以未完成遷移的狀態回報正常啟動。
- 測試資料檔缺少必要欄位、欄位型別錯誤或包含重複識別值時，載入程序明確拒絕或回報錯誤，不靜默忽略或產生部分不一致資料。
- 重複載入必須維持相同資料集合；清除命令在目標不符合明確的本機／測試環境設定時必須拒絕執行，不得作用於非本機開發資料庫。
- 清除命令及可能觸發資料刪除的測試，即使目標符合本機 allow-list，也不得以環境設定或確認旗標代替使用者對該命令與目標的另行明確授權；未獲授權時不得執行刪除，相關允許清除結果標為待驗證。
- API 錯誤不得回傳堆疊追蹤、SQL、憑證、密碼或內部主機資訊。
- 範例設定未提供必要環境變數時，啟動錯誤須指出缺少哪類設定，但不顯示秘密值。
- 畫面在載入期間、回應成功但資料集為空、以及呼叫失敗時，均呈現彼此可辨識的狀態；測試資料標記不得只在成功時被誤當成領域資料標籤。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Repository MUST 提供可在單一工作區取得及管理前端、後端、本機環境設定與專案說明的骨架。
- **FR-002**: 系統 MUST 提供僅供本機或測試使用的固定測試資料流程，且每筆回應 MUST 帶有可辨識的測試用途標記。
- **FR-003**: 測試頁 MUST 使用繁體中文，並清楚說明所示資料是固定測試資料，不是漁港、魚種、漁季、價格或限制的真實內容。
- **FR-004**: 前端 MUST 透過單一具型別的 API 存取邊界讀取版本化測試端點；頁面或呈現元件 MUST NOT 各自直接發出未型別 HTTP 呼叫。瀏覽器 MUST NOT 直接連線資料庫。
- **FR-005**: 前端 MUST 呈現載入中、成功、失敗及明確測試資料標記；錯誤狀態 MUST 易於辨識，且不得以看似有效的測試內容掩蓋服務失敗。
- **FR-006**: 後端 MUST 提供 `/api/v1` 下的本機／測試用途端點，並以一致的成功及錯誤契約回應；回應 DTO MUST 與資料庫實體分離。
- **FR-007**: 後端 MUST 將 HTTP 處理、應用使用案例及資料存取責任分開；端點 MUST 驗證輸入，錯誤回應 MUST 不暴露堆疊追蹤、SQL、憑證或內部主機資訊。
- **FR-008**: 資料庫結構 MUST 由版控中的有序版本化遷移建立；空白本機資料庫啟動後端時 MUST 可套用初始遷移並提供測試資料讀取流程。
- **FR-009**: 固定測試資料 MUST 有版控格式、欄位定義與載入驗證規則；重複執行載入 MUST 保持相同資料內容及筆數，不得產生重複或不一致記錄。
- **FR-010**: 文件 MUST 說明如何載入、再次載入及清除本機測試資料。清除命令 MUST 檢查明確的本機／測試環境設定，目標不符合時拒絕執行；清除步驟 MUST 限定於本機開發資料，不得成為正式資料操作。agent 在執行任何可能刪除資料的命令或測試前 MUST 取得使用者對具體命令與目標的另行明確授權；未獲授權時 MUST 停止該驗證並標示待驗證。
- **FR-011**: 固定資料、設定範例與測試產物 MUST 不包含真實個資、真實密碼／憑證／權杖，或來源未授權的真實產品內容。
- **FR-012**: 本階段 MUST NOT 匯入或呈現任何實際漁港、魚種、漁季、價格或限制資料；亦 MUST NOT 提供地圖、真實領域查詢或面向公眾的產品功能。
- **FR-013**: 資料庫連線及必要服務設定 MUST 可由環境變數或本機設定提供；版控範例 MUST 使用明確假值，且本階段 API 的設定與啟動範圍 MUST 限定於本機／測試用途。
- **FR-014**: 前後端 MUST 各自提供測試及建置驗證；測試 MUST 涵蓋 API 成功與錯誤、持久化讀寫、遷移啟動，以及前端型別 API 存取層成功與失敗呈現。
- **FR-015**: 開發流程 MUST 以可觀察行為採 TDD 驗證本階段功能切片，並提供跨端本機冒煙及重啟重現流程。
- **FR-016**: 完成骨架後，前後端開發規範或 README MUST 記錄實際已執行成功的安裝、啟動、測試、lint、build、資料庫及冒煙命令，包含必要服務、執行目錄與結果；未實際驗證的命令 MUST 明確標示為未驗證或不列為可用命令。

### Key Entities

- **測試資料項目**：僅用於本機與測試流程的固定資料，具穩定識別值、符合檔案格式的欄位值及明確測試標記；不代表任何真實產品領域紀錄。
- **測試標記**：供 API 呼叫者及使用者辨認內容為測試用途的欄位或標示，其語意必須隨資料回應保留並在介面呈現。
- **本機環境設定**：提供本機或測試服務連線所需的非秘密範例及設定說明；真實秘密由執行環境提供，不納入版控。
- **資料載入／重設程序**：依欄位規則驗證並可重複載入測試資料，或只清除本機開發資料的受限程序。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新的本機開發環境依文件完成全部啟動步驟後，可在一次端到端流程中看到至少一筆明確標示的測試資料；流程不需要手動修改資料庫 schema。
- **SC-002**: 在空白資料庫上啟動成功後，連續兩次載入固定資料的記錄筆數及每個欄位值完全一致，沒有重複記錄。
- **SC-003**: API 成功、API 錯誤、資料讀寫、遷移啟動及前端成功／失敗呈現的自動化驗證全部通過；跨端流程在服務重啟後仍能重現相同測試結果。
- **SC-004**: 前端讀取固定測試資料的 HTTP 呼叫均由具型別的集中存取邊界發出；瀏覽器的應用資料請求只走 `/api/v1`，且不直接連線資料庫。載入頁面所需的 HTML、JavaScript、CSS 等靜態資源請求不計入本項的應用資料請求。
- **SC-005**: 對版控測試資料、設定範例及文件的檢查確認：不含真實個資、憑證或未授權來源資料，也沒有把測試值描述成真實領域內容。
- **SC-006**: 完成時 README 或前後端開發規範中列出的每一個本機基線命令，都已在本次明確記錄的單一目標作業系統實際執行成功，該目標 OS 的本機基線命令須全數成功；若因環境限制不能驗證，該命令及限制明確記為未驗證，且不得宣稱該目標 OS 符合完整驗收。macOS、Linux、Windows 中其餘未實測的平台須逐一標記「待驗證」，不得宣稱跨平台已驗收；這不否定已實測目標 OS 的階段結果。

## Assumptions

- 本規格採用已同步至目前憲章、八階段開發計畫及產品規劃的八階段交付順序，以本機前後端骨架為第一階段；本 feature 僅涵蓋第一階段本機測試骨架，不擴張至後續產品功能。
- 本階段服務對象是 repository 維護者與開發者，目的在建立後續功能所需的可重現工程基礎，不面向一般網站訪客。
- 產品技術方向已由專案架構文件指定為 Angular 21、Spring Boot 模組化單體、PostgreSQL 與 Flyway；本規格將其視為使用者明示的技術限制，而非尚待挑選的方案。
- 本機測試資料使用少量人工製作的中性假資料，不含真實港名、魚名、行情、漁季、限制、個資、憑證或來源內容；示例文字及數值均不得造成真實資料的印象。
- 初始測試資料以受版本控制的載入來源提供，資料庫 schema 以版本化遷移提供；資料載入與 schema 遷移的責任及順序由規劃階段定義。
- 本階段不需要管理登入、一般會員、正式部署、公開資料服務、地圖、真實領域查詢、內容管理或自動擷取外部資料。
- 提供的 shell 命令基線是待實作後核對及驗證的介面；若生成工具或版本要求不同命令，須以實際成功結果更新文件。
