# 架構決策

本頁記錄目前計畫採用的架構預設。它們指引初期實作，不代表所有部署細節已定案。

## 已採用的預設

| 主題 | 決策 | 理由與邊界 |
| --- | --- | --- |
| Repository | 前後端放在單一 monorepo | 共用版本控制與文件入口，前端及後端仍有獨立目錄和交付邊界。 |
| 後端部署形態 | Spring Boot 模組化單體 | 初期以單一後端服務提供 API，按領域保持內部模組界線，不預先拆分微服務。 |
| API | 版本化 REST，前綴為 `/api/v1` | 前後端以明確 HTTP 資源契約協作；不相容契約變更另行規劃版本。 |
| 資料庫 | PostgreSQL | 作為核心領域資料及關聯的持久化資料庫。 |
| Schema 遷移 | Flyway | 以版本化遷移管理資料庫結構變更，隨後端部署流程套用。 |
| 前後端部署 | Angular 前端與 Spring Boot 後端可獨立建置及部署 | 允許各自設定交付，同時維持受版本管理的 REST 契約。 |
| 管理端安全 | Spring Security 在後端保護管理 API | 身分與權限必須由伺服器驗證，前端限制不能作為安全邊界。 |
| 使用者範圍 | 不含一般會員功能 | 公開內容可匿名瀏覽；管理者身分只為內容維護用途，並不擴張為會員系統。 |

## 明確不在目前範圍

- 不拆分微服務，也不新增服務間訊息佇列或事件平台。
- 不建立一般會員註冊、登入、個人資料或會員授權模型。
- 不預先固定完整資料欄位、資料表、索引、DTO 或 API 篩選參數。
- 不預先指定管理認證供應商、雲端平台、網域、CI/CD 或正式環境拓樸。
- 不在這份文件工作中建立 `frontend/`、`backend/` 程式骨架。

## 待後續決策

| 待決事項 | 決定時機或考量 |
| --- | --- |
| 管理者認證提供者與登入流程 | 開始實作管理登入時，依部署環境、安全需求及帳號管理方式選擇。 |
| 管理角色細分與管理帳號生命週期 | 確認實際維護者人數、權限分工及帳號開通方式後決定。 |
| 雲端部署平台與前後端發布流程 | 確認預算、維運能力、區域及環境需求後決定；必須保留前後端可獨立部署。 |
| 管理端認證的瀏覽器憑證、CSRF 與 CORS 策略 | 在認證方式、前後端網域及部署拓樸明確後共同設計。 |
| 魚類、漁港、漁業文化間的具體關聯基數及刪除政策 | 依內容編輯、公開查詢與資料維護情境確認，不先固定為特定 schema。 |
| API 分頁、搜尋、排序及錯誤格式 | 依前端使用情境及 API 契約實作需求確認，保持 `/api/v1` 的相容性規則。 |

決定待決事項時，更新本頁及相關架構文件，讓目錄建議、API 邊界與實作保持一致。
