# Harbor of Fish 共同開發規範

本文件規定前後端共同遵守的 TDD、API 契約、產品資料及交付要求。開發者與 AI agent 在實作時**必須**同時遵守工作範圍對應的[前端開發規範](frontend-development-standards.md)或[後端開發規範](backend-development-standards.md)；跨前後端的工作須遵守兩份。repository 根目錄的 `AGENTS.md` 另規定 runner、reviewer、工作區保護及 Git 授權流程，本文件不取代該流程。

目前架構文件描述預定方向，前後端骨架、測試工具及完整程式結構尚未建立。下列規則約束未來開發，不代表已有應用程式測試、lint 或 build 命令。

## 共同設計原則

- 命名**必須**使用產品與領域文件中的詞彙，清楚區分魚類、漁港、漁業文化、發布狀態、代表性漁季、批發價格及科普示意等概念。不得以缺值推導「沒有魚」，或將資料的代表性、批發性、示意性寫成已證實的即時事實。
- 模組、元件與函式**必須**有清楚的責任及資料所有者。跨模組協作使用明確介面；只有已出現的重複行為、變化點或隔離需求足以說明時，才引入共用層、介面或其他抽象，不為預想需求建立通用框架。
- 契約、來源資料意義、使用者可觀察行為或限制變動時，**必須**同步更新適用的測試、API／領域文件與產品說明；若影響架構預設或待決事項，也須更新架構決策文件。

## TDD 與測試要求

### 適用範圍與順序

新增功能、修正 bug、改變 API 行為或實作領域規則時，**必須**先確認公開測試介面與可觀察的驗收行為，再逐一完成小的行為切片：

1. 描述使用者、API 呼叫者或外部系統能觀察的一項結果，先寫驗證該結果的測試。
2. 執行測試，確認它因預期行為尚未實作而失敗（紅燈）。編譯、設定或測試本身錯誤不算有效紅燈，須先修正。
3. 只加入使該切片通過的最小實作，重跑相關測試確認綠燈。
4. 再處理下一個行為；行為完成後整理重複或不清楚的程式碼，並重跑受影響測試。

不得先批量寫完所有測試，再一次完成實作。發現既有行為不符需求時，先以外部可觀察的失敗案例固定問題，再修正程式。

### 測試品質與邊界

- 測試名稱、測試資料與失敗訊息**必須**說明情境及預期行為；預期值以需求、已知案例或明確邊界值為依據。測試應從公開介面觀察結果，不得以私有方法、內部呼叫次數、執行順序或照抄實作公式的斷言代替行為驗證。
- 僅在不可控的外部邊界（例如第三方服務、時鐘、檔案或必要的資料庫／HTTP 邊界）替換依賴。不得為觀察內部呼叫而替換應用程式內每個服務；持久化契約能使用實際測試資料庫驗證時，應優先驗證真實行為。
- 測試層次依功能觸及的風險與公開介面選擇：前端互動與 API 呈現見[前端規範](frontend-development-standards.md)，後端領域、HTTP、授權與資料庫見[後端規範](backend-development-standards.md)。跨前後端的主要使用流程，在具備執行環境後依產品階段建立端到端驗收；端到端測試不能取代較小範圍的領域及介面測試。
- 不設定缺乏產品或工程依據的固定覆蓋率數字。交付時說明關鍵行為由哪些測試驗證，以及尚未涵蓋的風險。

### 可驗證的例外

純文件變更不需程式測試，但**必須**檢查連結、內容一致性與修改範圍。純視覺樣式變更若不改變互動或資料行為，可用適當的畫面檢視或視覺驗收；無行為變化的機械式整理可沿用相關測試、靜態檢查或編譯驗證。例外**必須**說明驗證方式與未執行項目；若改動影響使用者行為，仍須採 TDD。

## API、產品資料與安全

- 前後端以 `/api/v1` 版本化 REST 契約協作。路徑、請求、回應、錯誤與存取政策**必須**有文件及相應測試；相容性變更留在既有版本，無法相容的變更須另行規劃版本，不可靜默改變既有語意。
- 公開查詢與管理寫入**必須**在端點與授權政策上區分。公開 API 只可提供已發布且可公開的內容；管理 CRUD、發布、下架及刪除僅於相應需求確立後實作，並由後端授權。前端限制不能取代伺服器端驗證。
- 展示的漁港、魚種、漁季、價格、限制與科普內容**必須**保留適用的來源、涵蓋期間、查證或更新時間、缺值及限制資訊。來源不足時標示待查或未知，不自行補造內容。
- API 與畫面**必須**保留缺值語意：代表性漁季不是實際月別漁獲；沒有漁季資料不等於該月沒有魚；批發行情不是零售價格；價格缺值不是零；洋流科普示意不是即時海況或漁獲預測。
- 真實密碼、憑證、存取權杖及第三方私密金鑰**不得**提交到 repository、回傳至瀏覽器或寫入一般日誌。範例設定只可使用明確假值。必要的診斷資料應遮蔽或去識別化。
- API 行為變更時，**必須**同步檢查前端型別與呈現、後端契約、相關測試、文件、版本相容性及公開資料界線。

## 工具與交付

建立前後端骨架並選定工具後，維護者**必須**在對應端的開發規範記錄已實際確認可執行的安裝、啟動、測試、lint、build 命令與結果，或直接連到 repository 根目錄 `README.md` 中對應的實測段落；兩種方式均須可查到執行目錄、必要服務、實際版本、命令及結果。前端規範須承載或連結前端測試與瀏覽器驗收證據，後端規範須承載或連結後端測試、資料庫／Flyway 與 API 契約驗證證據。根目錄 `README.md` 彙整單一目標 OS 的跨端啟動、冒煙、重啟及完整驗收結果；若端別實測紀錄位於開發規範，README 須直接連到該紀錄，不能與開發規範互相連結而沒有實際結果。未執行或未成功的命令明記「待驗證」與原因；現有文件與 orchestrator 驗證命令不得冒充應用程式命令。

每次交付**必須**回報：完成的可觀察驗收行為與修改範圍、相關測試或例外驗證結果、適用的 lint／build／遷移結果、文件更新，以及未驗證的假設與風險。尚未執行或無法執行的項目須說明原因。
