# Harbor of Fish 八階段開發計畫

本文件規定交付順序與內部驗收閘門。[產品規劃](product-plan.md)描述產品功能及資料語意；其中原有的三個功能主題不再作為交付階段編號。階段一至八均為內部開發與驗收，全部通過後才可首次公開網站。列出的內容是待完成要求，不代表已有程式、資料或命令可用。

## 共同交付原則

- 前端採 Angular，後端採 Spring Boot 模組化單體，透過 `/api/v1` 溝通；PostgreSQL 儲存資料，Flyway 管理 schema。前端不直接連資料庫。
- 產品資料與素材須先確認來源、欄位、涵蓋範圍、授權、更新條件及缺值語意。沒有證據時標示未知或保持功能關閉，不自行補造內容。
- 漁季是有來源支持的代表性資訊，不是實際月別漁獲；批發行情不是零售價格；洋流故事是科普示意，不是即時海況或漁獲預測。
- 內容與程式依[共同開發規範](development-standards.md)、[前端規範](frontend-development-standards.md)及[後端規範](backend-development-standards.md)驗證。工具命令只在實際跑通後標為已驗證。

| 2 | 地點資料與內容底稿 | 核對官方漁港名錄、可查證停靠處，準備五區深度港口與約十二種魚種內容底稿 | 階段一的資料載入與來源記錄方式。 |
| 3 | 地圖與地點探索 | 手機地圖、列表、縣市篩選、地點搜尋、按需定位及地點摘要 | 階段二已核對的地點資料。 |
| 4 | 魚種深度港口與月份探索 | 魚種與深度港口內容、魚種搜尋及有來源支持的代表性月份探索 | 階段二內容底稿、階段三導覽。 |

## 第一階段：前後端架構建立

建立最小可重現的 monorepo 前後端骨架及本機環境。僅用自行編造、明確標示的固定測試資料，驗證 Angular → `/api/v1` Spring Boot API → PostgreSQL 的往返。回應與繁體中文測試頁都要標明「僅供測試」，不得暗示已有真實漁港、魚種、漁季、價格或限制資料。本階段不提供地圖、真實領域查詢、管理介面、會員功能或對外公開服務。詳細可觀察需求見[第一階段規格](../specs/001-local-fullstack-skeleton/spec.md)。

- **資料與環境**：建立本機 PostgreSQL、Flyway 初始遷移、版控測試資料及設定範例；真實個資、憑證與未授權來源內容不得納入。文件記錄資料格式、欄位驗證、載入、重複載入與僅限本機開發資料的重設方式。
- **前端**：以集中且具型別的 API 存取層讀取測試端點，設定本機 `/api` 代理或等效方式；畫面區分載入、成功、錯誤及測試用途。
- **後端**：提供本機／測試用端點與一致的錯誤回應；Controller、應用層及資料存取責任清楚，API DTO 不直接暴露資料庫實體。設定由環境變數或本機假值範例提供。
- **驗收**：依小切片 TDD 驗證 API 成功與錯誤、資料讀寫、空資料庫遷移、前端成功與失敗；連續載入兩次不產生重複或不一致，跨端冒煙流程在服務重啟後可重現。
- **命令文件**：骨架建立後，將實際執行成功的安裝、啟動、測試、lint、build、資料庫與冒煙命令寫入 README 或各端開發文件，註明版本、執行目錄與必要服務。下列命令預計在 repository 根目錄執行，只是待核對的候選介面，不代表目前可執行：

```sh
docker compose -f infra/compose.yaml up -d postgres
./mvnw -f backend/pom.xml spring-boot:run
npm --prefix frontend start -- --proxy-config proxy.conf.json
npm --prefix frontend test -- --watch=false
./mvnw -f backend/pom.xml verify
npm --prefix frontend run build
```

若生成專案的 wrapper、腳本、服務名稱或版本不同，應以實際跑通的命令替換。第一階段只有在乾淨本機環境能依文件完成資料庫、遷移、API、前端、測試與建置，並於瀏覽器看到明確標示的測試資料後，才算通過。

## 第二至第八階段的範圍

### 第二階段：地點資料與內容底稿

核對官方漁港名錄的名稱、類別、縣市、座標、涵蓋及授權。官方名錄以外的停靠處只在有可靠公開來源時納入，並與「漁港」分別標示。另準備北、中、南、東、離島各一個深度港口及約十二種野生海魚的內容底稿；名稱、來源與素材須先查證，不以候選名單冒充已確認內容。

### 第三階段：地圖與地點探索

以已核對地點資料提供手機地圖、可操作列表、縣市篩選、地點搜尋、地點摘要及使用者主動點擊後的定位。拒絕定位仍可手動探索；地圖與列表選取狀態同步。此階段不以缺少月份資料推論沒有魚。

### 第四階段：魚種深度港口與月份探索

發布有來源支持的深度港口與魚種內容，提供魚種搜尋及月份探索。月份只表示已查證的代表性漁季；未知與待查不得顯示成「該月沒有魚」。文字與素材須保留來源、適用期間及限制。

### 第五階段：批發價格與趨勢

查證批發行情來源的魚種、市場、月份、單位、統計口徑、缺值、授權與更新方式。目標檢視最近六十個完整月份；來源不足時縮小實際可呈現期間，不補造價格。僅在來源自行提供且口徑清楚的整體月價存在時使用整體趨勢為預設，否則以資料完整的單一市場為預設並明示市場。確認來源可可靠取得且條款允許後，每月自動整理價格並保存官方修正記錄；條件未滿足前不得標示為可用。

### 第六階段：當季探索建議

建議是「當季探索」，不承諾現貨、零售便宜或一定可購得。每天檢查核准的主管機關禁漁、保育及其他限制來源；只有魚種、地區和期間可可靠判讀時才啟用。限制來源失效或公告無法解析時停止顯示建議，不以人工檢查代替故障後的恢復條件。至少三種魚種通過查核才啟用，並說明漁季、批發價格及資料限制如何影響理由。

### 第七階段：洋流故事內容與 API

查證洋流科普與素材權利，完成一則「臺灣周邊洋流總覽」故事及可追溯的港口、魚種關聯，提供已發布內容的讀取契約。故事與圖像必須標示為科普示意，不得表述成即時海況或漁獲預測。

### 第八階段：故事互動與全站驗收

完成手機直向故事卡、導覽與返回流程，驗證窄螢幕、鍵盤替代操作、來源與限制標示，以及地圖、魚種、價格、建議和故事的跨功能流程。階段一至八的內部驗收全部完成後，再辦理首次公開前檢查；此前不建立提早公開的路徑。

## 待各階段確認

具體地點與魚種名單、外部資料格式與授權、價格涵蓋期間、限制公告的可機器判讀性、素材使用權及正式部署方式，均須在對應階段以來源與實測結果確認。查證失敗時應縮小範圍、標示未知或保持相關功能關閉，不得將本計畫視為已取得資料或已完成產品驗收。
